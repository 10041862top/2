# 第 4 階段手冊 — 質量與加固

> **時長**：3-7 天 | **智能體**：8 個 | **守門人**：現實檢驗者（唯一權威）

---

## 目標

最後的質量考驗。現實檢驗者默認判定是"需要改進"——你必須用壓倒性的證據來證明可以上生產。這個階段存在的意義是：首次實現通常需要 2-3 輪修改，這很正常。

## 前提條件

- [ ] 第 3 階段質量門禁通過（所有任務都 QA 過）
- [ ] 收到第 3 階段交接包
- [ ] 所有功能已實現並單獨驗證

## 關鍵心態

> **現實檢驗者的默認判定是"需要改進"。**
>
> 這不是悲觀——是務實。上生產需要：
> - 完整的用戶旅程端到端跑通
> - 跨設備一致性（桌面、平板、手機）
> - 壓力下的性能表現（不只是正常情況）
> - 安全驗證（不是"我們加了認證"就行）
> - 需求合規（每條需求都滿足，不是大部分）
>
> 第一輪拿 B/B+ 是正常的。

## 智能體激活順序

### 第一步：證據收集（第 1-2 天，全部並行）

#### 證據收集者 — 全面視覺證據
```
激活證據收集者，為 [項目] 做全面系統證據收集。

交付要求：
1. 完整截圖套件：
   - 桌面端（1920x1080）— 每個頁面/視圖
   - 平板（768x1024）— 每個頁面/視圖
   - 手機（375x667）— 每個頁面/視圖
2. 交互證據：
   - 導航流程（點擊前後）
   - 表單交互（空白、填寫、提交、錯誤狀態）
   - 彈窗/對話框交互
   - 手風琴/可展開內容
3. 主題證據：
   - 亮色模式 — 所有頁面
   - 暗色模式 — 所有頁面
   - 系統偏好檢測
4. 錯誤狀態證據：
   - 404 頁面
   - 表單校驗錯誤
   - 網絡錯誤處理
   - 空狀態

格式：截圖證據包 + test-results.json
時間線：2 天
```

#### API 測試員 — 全量 API 迴歸
```
激活 API 測試員，為 [項目] 做完整的 API 迴歸測試。

交付要求：
1. 端點回歸套件：
   - 所有端點測試（GET, POST, PUT, DELETE）
   - 認證/授權驗證
   - 輸入校驗測試
   - 錯誤響應驗證
2. 集成測試：
   - 服務間通信
   - 數據庫操作驗證
   - 外部 API 集成
3. 邊界情況測試：
   - 限流行為
   - 大負載處理
   - 併發請求處理
   - 畸形輸入處理

格式：API 測試報告，每個端點通過/不通過
時間線：2 天
```

#### 性能基準師 — 壓力測試
```
激活性能基準師，為 [項目] 做壓力測試。

交付要求：
1. 10 倍預期流量的壓力測試：
   - 響應時間分佈（P50, P95, P99）
   - 壓力下的吞吐量
   - 壓力下的錯誤率
   - 資源消耗（CPU、內存、網絡）
2. Core Web Vitals 測量：
   - LCP（最大內容繪製）< 2.5s
   - FID（首次輸入延遲）< 100ms
   - CLS（累積佈局偏移）< 0.1
3. 數據庫性能：
   - 查詢執行時間
   - 連接池使用率
   - 索引有效性
4. 極限測試結果：
   - 找到系統斷點
   - 優雅降級行為
   - 過載後恢復時間

格式：性能認證報告
時間線：2 天
```

#### 法務合規員 — 最終合規審計
```
激活法務合規員，為 [項目] 做最終合規審計。

交付要求：
1. 隱私合規驗證：
   - 隱私政策準確性
   - 知情同意管理功能
   - 用戶數據權利實現
   - Cookie 同意實現
2. 安全合規：
   - 數據加密（靜態和傳輸中）
   - 認證安全性
   - 輸入過濾
   - OWASP Top 10 檢查
3. 監管合規：
   - GDPR 要求（如適用）
   - CCPA 要求（如適用）
   - 行業特定要求
4. 無障礙合規：
   - WCAG 2.1 AA 驗證
   - 屏幕閱讀器兼容性
   - 鍵盤導航

格式：合規認證報告
時間線：2 天
```

### 第二步：分析（第 3-4 天，並行，第一步完成後）

#### 測試結果分析師 — 質量指標彙總
```
激活測試結果分析師，為 [項目] 做質量指標彙總。

輸入：第一步的全部報告
交付要求：
1. 彙總質量儀表盤：
   - 總體質量評分
   - 分類明細（視覺、功能、性能、安全、合規）
   - 問題嚴重度分佈
   - 趨勢分析（如果有多輪測試）
2. 問題優先級排序：
   - 嚴重問題（上生產前必須修）
   - 高優問題（上生產前應該修）
   - 中等問題（下個 Sprint 修）
   - 低優問題（加到待辦列表）
3. 風險評估：
   - 上生產就緒概率
   - 剩餘風險區域
   - 建議的緩解措施

格式：質量指標儀表盤
時間線：1 天
```

#### 工作流優化師 — 流程效率復盤
```
激活工作流優化師，為 [項目] 做流程效率復盤。

輸入：第 3 階段執行數據 + 第一步的發現
交付要求：
1. 流程效率分析：
   - 開發-測試循環效率（首次通過率、平均重試次數）
   - 瓶頸識別
   - 不同問題類型的解決耗時
2. 改進建議：
   - 第 6 階段運營的流程改進
   - 自動化機會
   - 質量改進建議

格式：優化建議報告
時間線：1 天
```

#### 基礎設施運維師 — 生產就緒檢查
```
激活基礎設施運維師，為 [項目] 做生產就緒檢查。

交付要求：
1. 生產環境驗證：
   - 所有服務健康且有響應
   - 自動伸縮已配置並測試
   - 負載均衡配置已驗證
   - SSL/TLS 證書有效
2. 監控驗證：
   - 所有關鍵指標在收集
   - 告警規則已配置並測試
   - 儀表盤訪問已驗證
   - 日誌聚合正常
3. 災難恢復驗證：
   - 備份系統可用
   - 恢復流程已文檔化並測試
   - 故障切換機制已驗證
4. 安全驗證：
   - 防火牆規則已審查
   - 訪問控制已驗證
   - 密鑰管理已確認
   - 漏洞掃描通過

格式：基礎設施就緒報告
時間線：1 天
```

### 第三步：最終判定（第 5-7 天，串行）

#### 現實檢驗者 — 最終判定
```
激活現實檢驗者，為 [項目] 做最終集成測試。

以下流程不能跳過：

第一步：現實檢查命令
- 驗證實際做出了什麼（ls, grep 檢查聲稱的功能）
- 聲稱的功能與需求文檔交叉核對
- 跑一遍全面的截圖採集
- 審查第一步和第二步的所有證據

第二步：QA 交叉驗證
- 審查證據收集者的發現
- 與 API 測試員結果交叉核對
- 驗證性能基準師數據
- 確認法務合規員的發現

第三步：端到端系統驗證
- 測試完整用戶旅程（不是單個功能）
- 在所有設備上驗證響應式行為
- 端到端檢查交互流程
- 審查實際性能數據

第四步：需求對照檢查
- 引用原始需求文檔的原文
- 與實際實現證據對照
- 記錄需求與現實之間的每一個差距
- 不做假設——只看證據

判定選項：
- 就緒：壓倒性的證據表明可以上生產（首次通過很少見）
- 需要改進：發現具體問題，附修復清單（正常情況）
- 未就緒：架構層面有大問題，需要回到第 1/2 階段

格式：基於現實的集成報告
默認：需要改進——除非有相反的壓倒性證據
```

## 質量門禁 — 最終關卡

| # | 標準 | 閾值 | 需要的證據 |
|---|------|------|-----------|
| 1 | 用戶旅程完整 | 所有關鍵路徑端到端跑通 | 現實檢驗者截圖 |
| 2 | 跨設備一致性 | 桌面 + 平板 + 手機都正常 | 響應式截圖 |
| 3 | 性能認證通過 | P95 < 200ms, LCP < 2.5s, 可用性 > 99.9% | 性能基準師報告 |
| 4 | 安全驗證通過 | 零嚴重漏洞 | 安全掃描 + 合規報告 |
| 5 | 合規認證通過 | 所有監管要求都滿足 | 法務合規員報告 |
| 6 | 需求合規 | 100% 的需求都實現了 | 逐條驗證 |
| 7 | 基礎設施就緒 | 生產環境已驗證 | 基礎設施運維師報告 |

## 門禁決策

**唯一權威**：現實檢驗者

### 如果判定"就緒"（進入第 5 階段）：
```markdown
## 第 4 階段 → 第 5 階段交接包

### 給上線團隊的：
- 現實檢驗者認證報告
- 性能認證
- 合規認證
- 基礎設施就緒報告
- 已知限制（如果有的話）

### 給增長黑客的：
- 產品已可交付用戶
- 營銷話術用的功能列表
- 增加可信度的性能數據

### 給 DevOps 自動化師的：
- 生產部署已批准
- 藍綠部署方案
- 回滾流程已確認
```

### 如果判定"需要改進"（回到第 3 階段）：
```markdown
## 第 4 階段 → 第 3 階段返工包

### 修復清單（來自現實檢驗者）：
1. [嚴重問題 1]：[描述 + 證據 + 修復說明]
2. [嚴重問題 2]：[描述 + 證據 + 修復說明]
3. [高優問題 1]：[描述 + 證據 + 修復說明]
...

### 流程：
- 問題進入開發-測試循環（第 3 階段機制）
- 每個修復都要通過證據收集者 QA
- 所有修復完成後 → 回到第 4 階段第三步
- 現實檢驗者用更新後的證據重新評估

### 預期：2-3 輪修改是正常的
```

### 如果判定"未就緒"（回到第 1/2 階段）：
```markdown
## 第 4 階段 → 第 1/2 階段返工包

### 發現的架構問題：
1. [根本性問題]：[為什麼第 3 階段修不了]
2. [結構性問題]：[架構層面需要改什麼]

### 建議行動：
- [ ] 修改系統架構（第 1 階段）
- [ ] 重建基礎（第 2 階段）
- [ ] 縮小範圍重新定義（第 1 階段）

### 需要工作室製片人決策
```

---

*當現實檢驗者給出"就緒"判定且有壓倒性證據時，第 4 階段結束。"需要改進"是首輪預期的正常結果——說明系統在跑，但還需要打磨。*
