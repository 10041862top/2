# 第 3 階段手冊 — 構建與迭代

> **時長**：2-12 周（視範圍而定）| **智能體**：15-30+ | **守門人**：智能體編排者

---

## 目標

通過持續的開發-測試循環實現所有功能。每個任務都經過驗證後才進入下一個。這個階段是工作量最大的階段——也是 NEXUS 編排價值發揮最大的地方。

## 前提條件

- [ ] 第 2 階段質量門禁通過（基礎已驗證）
- [ ] Sprint 排序師的待辦列表（含 RICE 評分）已就緒
- [ ] CI/CD 流水線可用
- [ ] 設計系統和組件庫就緒
- [ ] API 骨架 + 認證系統就緒

## 開發-測試循環 — 核心機制

智能體編排者通過這個循環管理每一個任務：

```
對於 sprint_backlog 中的每個任務（按 RICE 分數排序）：

  1. 分配任務給合適的開發智能體（見分配矩陣）
  2. 開發者實現任務
  3. 證據收集者測試任務
     - 視覺截圖（桌面、平板、手機）
     - 按驗收標準做功能驗證
     - 品牌一致性檢查
  4. 如果判定 == 通過：
       標記任務完成
       進入下一個任務
     否則如果判定 == 不通過 且 重試次數 < 3：
       把 QA 反饋發給開發者
       開發者修復具體問題
       回到第 3 步
     否則如果 重試次數 >= 3：
       升級給智能體編排者
       編排者決定：重新分配、拆分、推遲或接受
  5. 更新流水線狀態報告
```

## 並行構建軌道

NEXUS-Full 部署時，四條軌道同時跑：

### 軌道 A：核心產品開發
```
管理者：智能體編排者（開發-測試循環）
智能體：前端開發者、後端架構師、AI 工程師、
        移動應用開發者、高級開發者
QA：證據收集者、API 測試員、測試結果分析師

Sprint 節奏：2 週一個 Sprint
每天：任務實現 + QA 驗證
Sprint 結束：Sprint 回顧 + 復盤
```

### 軌道 B：增長與營銷準備
```
管理者：項目牧羊人
智能體：增長黑客、內容創作者、社交媒體策略師、
        應用商店優化師

Sprint 節奏：與軌道 A 里程碑對齊
活動內容：
- 增長黑客 → 設計病毒式傳播和推薦機制
- 內容創作者 → 準備上線內容管道
- 社交媒體策略師 → 規劃跨平臺活動
- 應用商店優化師 → 準備商店頁面（如果是移動端）
```

### 軌道 C：質量與運營
```
管理者：智能體編排者
智能體：證據收集者、API 測試員、性能基準師、
        工作流優化師、實驗追蹤員

持續活動：
- 證據收集者 → 每個任務都做截圖 QA
- API 測試員 → 每個 API 任務都做端點驗證
- 性能基準師 → 定期壓力測試
- 工作流優化師 → 發現流程改進機會
- 實驗追蹤員 → 為已驗證的功能搭 A/B 測試
```

### 軌道 D：品牌與體驗打磨
```
管理者：品牌守護者
智能體：UI 設計師、品牌守護者、視覺敘事師、
        趣味注入師

觸發式活動：
- UI 設計師 → QA 發現視覺問題時做組件打磨
- 品牌守護者 → 定期品牌一致性審計
- 視覺敘事師 → 功能完成後做視覺敘事素材
- 趣味注入師 → 微交互和愉悅感設計
```

## Sprint 執行模板

### Sprint 規劃（第 1 天）

```
Sprint 排序師激活：
1. 用更新後的 RICE 分數審查待辦列表
2. 按團隊速度選擇 Sprint 內容
3. 把任務分配給開發智能體
4. 識別依賴和執行順序
5. 設定 Sprint 目標和成功標準

產出：帶任務分配的 Sprint 計劃
```

### 每日執行（第 2 天到第 N-1 天）

```
智能體編排者管理：
1. 檢查當前任務狀態
2. 執行開發-測試循環
3. 識別並解決阻塞
4. 進度追蹤和彙報

狀態報告格式：
- 今天完成的任務：[列表]
- QA 中的任務：[列表]
- 開發中的任務：[列表]
- 被阻塞的任務：[列表 + 原因]
- QA 通過率：[X/Y]
```

### Sprint 回顧（第 N 天）

```
項目牧羊人主持：
1. 演示已完成的功能
2. 審查每個任務的 QA 證據
3. 收集利益相關方反饋
4. 根據學到的東西更新待辦列表

參與者：所有活躍智能體 + 利益相關方
產出：Sprint 回顧總結
```

### Sprint 復盤

```
工作流優化師主持：
1. 哪些做得好？
2. 哪些可以改進？
3. 下個 Sprint 我們改什麼？
4. 流程效率指標

產出：復盤行動項
```

## 編排者決策邏輯

### 任務失敗處理

```
當任務 QA 不通過時：
  如果 重試次數 == 1：
    → 把具體的 QA 反饋發給開發者
    → 開發者只修被指出的問題
    → 重新提交 QA

  如果 重試次數 == 2：
    → 發送累計 QA 反饋
    → 考慮：這個開發智能體是不是合適的人選？
    → 開發者帶著更多上下文修復
    → 重新提交 QA

  如果 重試次數 == 3：
    → 升級
    → 選項：
      a) 重新分配給另一個開發智能體
      b) 拆分成更小的子任務
      c) 換實現思路/架構
      d) 接受當前狀態（記錄已知限制）
      e) 推遲到後面的 Sprint
    → 記錄決策和原因
```

### 並行任務管理

```
當多個任務之間沒有依賴時：
  → 同時分配給不同的開發智能體
  → 每個跑獨立的開發-測試循環
  → 編排者同時追蹤所有循環
  → 按依賴順序合併已完成的任務

當任務有依賴時：
  → 等依賴任務通過 QA
  → 然後分配依賴任務
  → 交接時帶上依賴的上下文
```

## 質量門禁檢查清單

| # | 標準 | 證據來源 | 狀態 |
|---|------|---------|------|
| 1 | 所有 Sprint 任務通過 QA（100% 完成） | 每個任務的證據收集者截圖 | |
| 2 | 所有 API 端點已驗證 | API 測試員迴歸報告 | |
| 3 | 性能基線達標（P95 < 200ms） | 性能基準師報告 | |
| 4 | 品牌一致性已驗證（95%+ 合規） | 品牌守護者審計 | |
| 5 | 沒有嚴重 bug（零 P0/P1 開放） | 測試結果分析師摘要 | |
| 6 | 所有驗收標準都滿足 | 逐任務驗證 | |
| 7 | 所有 PR 都做了 Code Review | Git 歷史證據 | |

## 門禁決策

**守門人**：智能體編排者

- **通過**：功能完整的應用 → 激活第 4 階段
- **繼續**：還需要更多 Sprint → 繼續第 3 階段
- **升級**：系統性問題 → 工作室製片人介入

```markdown

- 性能基準師基線數據

- 伸縮配置需求
```
