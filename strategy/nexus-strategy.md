## 1. 策略基礎

### 1.1 NEXUS 解決什麼問題

單個智能體很強。但沒有協調的話，它們會產出：
- 相互矛盾的架構決策
- 跨部門的重複勞動
- 交接邊界的質量斷層
- 沒有共享上下文和組織記憶

**NEXUS 消滅這些失敗模式**，明確定義：
- **誰**在每個階段激活
- **做什麼**，產出給誰
- **什麼時候**交接，交給誰
- **怎麼**在推進前驗證質量
- **為什麼**每個智能體存在於流水線中（不帶閒人）

### 1.2 核心原則

| 原則 | 說明 |
|------|------|
| **流水線完整性** | 沒過質量門禁的階段不能推進 |
| **上下文連續性** | 每次交接都帶完整上下文——沒有智能體冷啟動 |
| **並行執行** | 獨立的工作流同時跑，壓縮工期 |
| **證據高於口說** | 所有質量評估要拿出證據，不是口頭聲明 |
| **快速失敗，快速修復** | 每個任務最多重試 3 次就升級 |
| **單一信息源** | 一份需求文檔、一份任務清單、一份架構文檔 |

     ┌────────▼──────┐ ┌──────▼───────┐ ┌──────▼──────────┐

              │                │                │

### 2.3 激活模式

NEXUS 支持三種部署配置：

| 模式 | 活躍智能體數 | 適用場景 | 時間線 |
|------|------------|---------|--------|
| **NEXUS-Full** | 全部 | 企業級產品上線，完整生命週期 | 12-24 周 |
| **NEXUS-Sprint** | 15-25 | 功能開發，MVP 構建 | 2-6 周 |
| **NEXUS-Micro** | 5-10 | Bug 修復，內容活動，單一交付物 | 1-5 天 |

## 3. 第 0 階段 — 情報與發現

> **目標**：投入資源之前先搞清楚情況。問題沒驗證之前不動手。

### 3.1 活躍智能體

| 智能體 | 階段角色 | 主要產出 |
|--------|---------|---------|
| **趨勢研究員** | 市場情報負責人 | 含 TAM/SAM/SOM 的市場分析報告 |
| **反饋分析師** | 用戶需求分析 | 含痛點的綜合反饋報告 |
| **UX 研究員** | 用戶行為分析 | 含用戶畫像和旅程圖的調研報告 |
| **數據分析師** | 數據基礎評估 | 含可用信號的數據審計報告 |
| **法務合規員** | 監管掃描 | 合規要求矩陣 |
| **工具評估師** | 技術版圖 | 技術棧評估 |

### 3.2 並行工作流

```
工作流 A：市場情報                      工作流 B：用戶情報
├── 趨勢研究員                          ├── 反饋分析師
│   ├── 競爭格局                        │   ├── 多渠道反饋收集
│   ├── 市場規模（TAM/SAM/SOM）          │   ├── 情感分析
│   └── 趨勢生命週期圖譜                  │   └── 痛點排序
│                                       │
├── 數據分析師                          ├── UX 研究員
│   ├── 現有數據審計                     │   ├── 用戶訪談/問卷
│   ├── 信號識別                        │   ├── 用戶畫像構建
│   └── 基線指標                        │   └── 旅程圖繪製
│                                       │
└── 法務合規員                          └── 工具評估師
    ├── 監管要求                            ├── 技術評估
    ├── 數據處理約束                        ├── 自建 vs 採購分析
    └── 司法管轄區映射                      └── 集成可行性
```

### 3.3 第 0 階段質量門禁

**守門人**：高管摘要生成器

| 標準 | 閾值 | 需要的證據 |
|------|------|-----------|
| 市場機會已驗證 | TAM 超過最低可行閾值 | 趨勢研究員報告 + 來源 |
| 用戶需求已確認 | >= 3 個已驗證痛點 | 反饋分析師 + UX 研究員數據 |
| 監管路徑清晰 | 無阻塞性合規問題 | 法務合規員矩陣 |
| 數據基礎已評估 | 關鍵指標已識別 | 數據分析師審計 |
| 技術可行性已確認 | 技術棧已驗證 | 工具評估師評估 |

**產出**：高管摘要（不超過 500 字，SCQA 格式） → 決策：繼續 / 終止 / 調整方向

## 4. 第 1 階段 — 策略與架構

> **目標**：定義做什麼、怎麼搭、成功標準是什麼——一行代碼都不寫之前搞定。

### 4.1 活躍智能體

| 智能體 | 階段角色 | 主要產出 |
|--------|---------|---------|
| **工作室製片人** | 策略組合對齊 | 策略組合計劃 |
| **高級項目經理** | 需求轉任務 | 完整任務清單 |
| **Sprint 排序師** | 功能排序 | RICE 評分的待辦列表 |
| **UX 架構師** | 技術架構 + UX 基礎 | 架構文檔 + CSS 設計系統 |
| **品牌守護者** | 品牌識別系統 | 品牌基礎文檔 |
| **後端架構師** | 系統架構 | 系統架構文檔 |
| **AI 工程師** | AI/ML 架構（如適用） | ML 系統設計 |
| **財務追蹤員** | 預算和資源規劃 | 含 ROI 預測的財務計劃 |

### 4.2 執行順序

```
第一步：策略定調（並行）
├── 工作室製片人 → 策略組合計劃（願景、目標、ROI 指標）
├── 品牌守護者 → 品牌基礎（使命、價值觀、視覺識別系統）
└── 財務追蹤員 → 預算框架（資源配置、成本預測）

第二步：技術架構（並行，第一步完成後）
├── UX 架構師 → CSS 設計系統 + 佈局框架 + UX 結構
├── 後端架構師 → 系統架構（服務、數據庫、API）
├── AI 工程師 → ML 架構（模型、管道、推理策略）
└── 高級項目經理 → 任務清單（需求 → 任務，精確引用需求）

第三步：排優先級（串行，第二步完成後）
└── Sprint 排序師 → RICE 評分的待辦列表 + Sprint 分配
    ├── 輸入：任務清單 + 架構文檔 + 預算框架
    ├── 產出：排好序的 Sprint 計劃 + 依賴圖
    └── 驗證：工作室製片人確認策略對齊
```

### 4.3 第 1 階段質量門禁

**守門人**：工作室製片人 + 現實檢驗者（雙籤）

| 標準 | 閾值 | 需要的證據 |
|------|------|-----------|
| 架構覆蓋所有需求 | 100% 覆蓋 | 高級項目經理任務清單交叉核對 |
| 品牌系統完整 | Logo、顏色、字體、語調已定義 | 品牌守護者交付物 |
| 技術可行性已驗證 | 所有組件有實現路徑 | 後端架構師 + UX 架構師文檔 |
| 預算已批准 | 在組織約束範圍內 | 財務追蹤員計劃 |
| Sprint 計劃切合實際 | 基於速度的估算 | Sprint 排序師待辦列表 |

**產出**：批准的架構包 → 激活第 2 階段

## 6. 第 3 階段 — 構建與迭代

> **目標**：通過持續的開發-測試循環實現功能。每個任務驗證後才進入下一個。這是工作量最大的階段。

### 6.1 開發-測試循環

這是 NEXUS 的心臟。智能體編排者管理一個**逐任務的質量循環**：

```
┌─────────────────────────────────────────────────────────┐
│                   開發-測試循環                            │
│                                                          │
│  ┌──────────┐    ┌──────────┐    ┌──────────────────┐   │
│  │ 開發      │───▶│ 證據     │───▶│ 決策邏輯          │   │
│  │ 智能體    │    │ 收集者   │    │                   │   │
│  │           │    │ （QA）   │    │ 通過 → 下一個任務  │   │
│  │ 實現      │    │          │    │ 不通過 → 重試(<=3) │   │
│  │ 任務 N    │    │ 測試     │    │ 阻塞 → 升級       │   │
│  │           │◀───│ 任務 N   │◀───│                   │   │
│  └──────────┘    └──────────┘    └──────────────────┘   │
│       ▲                                    │             │
│       │            QA 反饋                  │             │
│       └────────────────────────────────────┘             │
│                                                          │
│  編排者追蹤：重試次數、QA 反饋、                             │
│  任務狀態、累計質量指標                                      │
└─────────────────────────────────────────────────────────┘
```

| 移動端 | 移動應用開發者 | 證據收集者 | UX 研究員 |
| AI/ML 功能 | AI 工程師 | 測試結果分析師 | 數據分析師 |
| 基礎設施 | DevOps 自動化師 | 性能基準師 | 基礎設施運維師 |
| 高級打磨 | 高級開發者 | 證據收集者 | 視覺敘事師 |

## 7. 第 4 階段 — 質量與加固

> **目標**：最後的質量考驗。現實檢驗者默認"需要改進"——你得用壓倒性的證據來證明可以上生產。

### 7.1 活躍智能體

| 智能體 | 階段角色 | 主要產出 |
|--------|---------|---------|
| **現實檢驗者** | 最終集成測試（默認"需要改進"） | 基於現實的集成報告 |
| **證據收集者** | 全面視覺證據 | 截圖證據包 |
| **性能基準師** | 壓力測試 + 優化 | 性能認證 |
| **API 測試員** | 全量 API 迴歸 | API 測試報告 |
| **測試結果分析師** | 彙總質量指標 | 質量指標儀表盤 |
| **法務合規員** | 最終合規審計 | 合規認證 |
| **基礎設施運維師** | 生產就緒檢查 | 基礎設施就緒報告 |
| **工作流優化師** | 流程效率復盤 | 優化建議 |

### 7.2 加固流程

```
第一步：證據收集（並行）
├── 證據收集者 → 全量截圖套件（桌面、平板、手機）
├── API 測試員 → 完整端點回歸
├── 性能基準師 → 10 倍預期流量壓力測試
└── 法務合規員 → 最終監管審計

第二步：分析（並行，第一步完成後）
├── 測試結果分析師 → 把所有測試數據彙總成質量儀表盤
├── 工作流優化師 → 找出剩餘的流程低效
└── 基礎設施運維師 → 生產環境驗證

第三步：最終判定（串行，第二步完成後）
└── 現實檢驗者 → 集成報告
    ├── 交叉驗證之前所有 QA 發現
    ├── 用截圖證據測試完整用戶旅程
    ├── 逐條驗證需求合規
    ├── 默認判定：需要改進
    └── 只有在所有標準都有壓倒性證據時才給"就緒"
```

### 7.3 第 4 階段質量門禁（最終關卡）

**守門人**：現實檢驗者（唯一權威）

| 標準 | 閾值 | 需要的證據 |
|------|------|-----------|
| 用戶旅程完整 | 所有關鍵路徑跑通 | 端到端截圖 |
| 跨設備一致性 | 桌面 + 平板 + 手機 | 響應式截圖 |
| 性能認證通過 | P95 < 200ms, 可用性 > 99.9% | 壓力測試結果 |
| 安全驗證通過 | 零嚴重漏洞 | 安全掃描報告 |
| 合規認證通過 | 所有監管要求都滿足 | 法務合規員報告 |
| 需求合規 | 100% 需求已實現 | 逐條驗證 |

**判定選項**：
- **就緒** — 可以上線（首輪通過很少見）
- **需要改進** — 回到第 3 階段修具體問題（正常情況）
- **未就緒** — 架構有大問題，回到第 1/2 階段

**預期**：首次實現通常需要 2-3 輪修改。B/B+ 的評分很正常也很健康。

| 1 → 2 | 架構門禁 | 工作室製片人 + 現實檢驗者 | 架構完整，品牌已定義，預算已批准，Sprint 計劃切實 |
| 2 → 3 | 基礎門禁 | DevOps 自動化師 + 證據收集者 | CI/CD 可用，骨架應用在跑，監控在線 |
| 3 → 4 | 功能門禁 | 智能體編排者 | 所有任務通過 QA，無嚴重 bug，性能基線達標 |
| 4 → 5 | 生產門禁 | 現實檢驗者（唯一權威） | 用戶旅程完整，跨設備一致，安全已驗證，需求合規 |
| 5 → 6 | 上線門禁 | 工作室製片人 + 數據分析師 | 部署成功，系統穩定，增長渠道活躍 |

### 12.2 門禁失敗處理

```
如果門禁不通過：
  ├── 守門人出具具體的失敗報告
  ├── 智能體編排者把失敗項路由給負責的智能體
  ├── 失敗項進入開發-測試循環（第 3 階段機制）
  ├── 最多 3 次門禁重試，超過就升級給工作室製片人
  └── 工作室製片人決定：修、砍範圍、還是帶風險接受
```
