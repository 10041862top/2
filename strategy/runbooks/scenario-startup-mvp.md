# 操作手冊：創業 MVP 構建

> **模式**：NEXUS-Sprint | **時長**：4-6 周 | **智能體**：18-22

---

## 場景

你要做一個創業 MVP——一個需要快速驗證產品市場契合度的新產品。速度很重要，但質量也不能丟。目標是 4-6 周內從想法到有真實用戶的上線產品。

## 智能體陣容

### 核心團隊（始終活躍）
| 智能體 | 角色 |
|--------|------|
| 智能體編排者 | 流水線控制器 |
| 高級項目經理 | 需求轉任務 |
| Sprint 排序師 | 待辦管理 |
| UX 架構師 | 技術基礎 |
| 前端開發者 | UI 實現 |
| 後端架構師 | API 和數據庫 |
| DevOps 自動化師 | CI/CD 和部署 |
| 證據收集者 | 每個任務都 QA |
| 現實檢驗者 | 最終質量門禁 |

### 增長團隊（第 3 周+ 激活）
| 智能體 | 角色 |
|--------|------|
| 增長黑客 | 獲客策略 |
| 內容創作者 | 上線內容 |
| 社交媒體策略師 | 社交媒體活動 |

### 支持團隊（按需）
| 智能體 | 角色 |
|--------|------|
| 品牌守護者 | 品牌識別 |
| 數據分析師 | 指標和儀表盤 |
| 快速原型師 | 快速驗證實驗 |
| AI 工程師 | 產品包含 AI 功能時 |
| 性能基準師 | 上線前壓力測試 |
| 基礎設施運維師 | 生產環境搭建 |

## 逐周執行

### 第 1 周：發現 + 架構（第 0 階段 + 第 1 階段壓縮版）

```
第 1-2 天：壓縮版發現
├── 趨勢研究員 → 快速競品掃描（1 天，不用出完整報告）
├── UX 架構師 → 核心用戶流程線框圖
└── 高級項目經理 → 需求轉任務清單

第 3-4 天：架構
├── UX 架構師 → CSS 設計系統 + 組件架構
├── 後端架構師 → 系統架構 + 數據庫 Schema
├── 品牌守護者 → 快速品牌基礎（顏色、字體、語調）
└── Sprint 排序師 → RICE 評分的待辦列表 + Sprint 計劃

第 5 天：基礎搭建
├── DevOps 自動化師 → CI/CD 流水線 + 環境
├── 前端開發者 → 項目腳手架
├── 後端架構師 → 數據庫 + API 骨架
└── 質量門禁：架構包通過
```

### 第 2-3 周：核心構建（第 2 階段 + 第 3 階段）

```
Sprint 1（第 2 周）：
├── 智能體編排者管理開發-測試循環
├── 前端開發者 → 核心 UI（認證、主視圖、導航）
├── 後端架構師 → 核心 API（認證、CRUD、業務邏輯）
├── 證據收集者 → 每個完成的任務都 QA
├── AI 工程師 → ML 功能（如適用）
└── 週末 Sprint 回顧

Sprint 2（第 3 周）：
├── 繼續跑開發-測試循環做剩餘功能
├── 增長黑客 → 設計病毒式傳播 + 推薦系統
├── 內容創作者 → 開始製作上線內容
├── 數據分析師 → 搭建數據追蹤和儀表盤
└── 週末 Sprint 回顧
```

### 第 4 周：打磨 + 加固（第 4 階段）

```
第 1-2 天：質量衝刺
├── 證據收集者 → 全量截圖套件
├── 性能基準師 → 壓力測試
├── 前端開發者 → 修 QA 問題
├── 後端架構師 → 修 API 問題
└── 品牌守護者 → 品牌一致性審計

第 3-4 天：現實檢查
├── 現實檢驗者 → 最終集成測試
├── 基礎設施運維師 → 生產就緒檢查
└── DevOps 自動化師 → 生產部署準備

第 5 天：門禁決策
├── 現實檢驗者判定
├── 如果"需要改進"：快速修復循環（2-3 天）
├── 如果"就緒"：開始上線
└── 高管摘要生成器 → 利益相關方簡報
```

### 第 5-6 周：上線 + 增長（第 5 階段）

```
第 5 周：上線
├── DevOps 自動化師 → 生產部署
├── 增長黑客 → 激活獲客渠道
├── 內容創作者 → 發佈上線內容
├── 社交媒體策略師 → 跨平臺活動
├── 數據分析師 → 實時監控
└── 客服響應者 → 用戶支持上線

第 6 周：優化
├── 增長黑客 → 分析和優化渠道
├── 反饋分析師 → 收集早期用戶反饋
├── 實驗追蹤員 → 啟動 A/B 測試
├── 數據分析師 → 第一週分析
└── Sprint 排序師 → 規劃迭代 Sprint
```

## 關鍵決策點

| 決策點 | 什麼時候 | 誰來決 |
|--------|---------|--------|
| 概念繼續/終止 | 第 2 天結束 | 工作室製片人 |
| 架構通過 | 第 4 天結束 | 高級項目經理 |
| MVP 功能範圍 | Sprint 規劃時 | Sprint 排序師 |
| 生產就緒 | 第 4 周第 5 天 | 現實檢驗者 |
| 上線時機 | 現實檢驗者給出"就緒"後 | 工作室製片人 |

## 成功標準

| 指標 | 目標 |
|------|------|
| 上線產品的時間 | <= 6 周 |
| 核心功能完成度 | MVP 範圍的 100% |
| 首批用戶入駐 | 上線 48 小時內 |
| 系統可用性 | 第一週 > 99% |
| 用戶反饋收集 | 前 2 周 >= 50 份 |

## 常見坑和怎麼避

| 坑 | 怎麼避 |
|----|--------|
| 構建階段範圍蔓延 | Sprint 排序師用 MoSCoW 管控——"Won't"就是不做 |
| 過度工程化追求擴展性 | 用快速原型師心態——先驗證，再考慮擴展 |
| 為了速度跳過 QA | 證據收集者每個任務都跑——沒有例外 |
| 沒有監控就上線 | 基礎設施運維師在第 1 周就搭好監控 |
| 沒有反饋收集機制 | 數據追蹤 + 反饋收集在 Sprint 1 就做進去 |
