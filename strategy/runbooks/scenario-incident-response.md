# 操作手冊：事故響應

> **模式**：NEXUS-Micro | **時長**：分鐘到小時 | **智能體**：3-8

---

## 場景

生產環境出問題了。用戶受影響了。速度很重要，但不能亂來。這個手冊覆蓋從發現到事後復盤的全流程。

## 嚴重度分級

| 級別 | 定義 | 舉例 | 響應時間 |
|------|------|------|---------|
| **P0 — 緊急** | 服務完全掛了、數據丟失、安全事件 | 數據庫損壞、DDoS 攻擊、認證系統掛了 | 立即（全員響應） |
| **P1 — 高** | 主要功能掛了、性能嚴重下降 | 支付處理掛了、50%+ 錯誤率、10 倍延遲 | < 1 小時 |
| **P2 — 中** | 次要功能掛了、有臨時方案 | 搜索不能用、非關鍵 API 報錯 | < 4 小時 |
| **P3 — 低** | 樣式問題、小不便 | 樣式 bug、錯別字、小的 UI 問題 | 下個 Sprint |

## 按嚴重度的響應團隊

### P0 — 緊急響應團隊
| 智能體 | 角色 | 行動 |
|--------|------|------|
| **基礎設施運維師** | 事故指揮官 | 評估範圍、協調響應 |
| **DevOps 自動化師** | 部署/回滾 | 需要的話執行回滾 |
| **後端架構師** | 根因排查 | 診斷系統問題 |
| **前端開發者** | 前端排查 | 診斷客戶端問題 |
| **客服響應者** | 用戶通知 | 更新狀態頁、通知用戶 |
| **高管摘要生成器** | 利益相關方通知 | 實時高管更新 |

### P1 — 高優響應團隊
| 智能體 | 角色 |
|--------|------|
| **基礎設施運維師** | 事故指揮官 |
| **DevOps 自動化師** | 部署支持 |
| **相關開發智能體** | 修復實現 |
| **客服響應者** | 用戶通知 |

### P2 — 中等響應
| 智能體 | 角色 |
|--------|------|
| **相關開發智能體** | 修復實現 |
| **證據收集者** | 驗證修復 |

### P3 — 低優響應
| 智能體 | 角色 |
|--------|------|
| **Sprint 排序師** | 加到待辦列表 |

## 事故響應流程

### 第一步：發現與分診（0-5 分鐘）

```
觸發條件：監控告警 / 用戶報告 / 智能體檢測到

基礎設施運維師：
1. 確認告警
2. 評估範圍和影響
   - 多少用戶受影響？
   - 哪些服務受影響？
   - 數據有沒有風險？
3. 確定嚴重度（P0/P1/P2/P3）
4. 激活對應的響應團隊
5. 創建事故頻道/線程

產出：事故分級 + 響應團隊已激活
```

### 第二步：排查（5-30 分鐘）

```
並行排查：

基礎設施運維師：
├── 檢查系統指標（CPU、內存、網絡、磁盤）
├── 查看錯誤日誌
├── 檢查最近的部署
└── 驗證外部依賴

後端架構師（P0/P1 時）：
├── 檢查數據庫健康
├── 查看 API 錯誤率
├── 檢查服務間通信
└── 定位故障組件

DevOps 自動化師：
├── 查看最近的部署歷史
├── 檢查 CI/CD 流水線狀態
├── 需要的話準備回滾
└── 驗證基礎設施狀態

產出：根因已確定（或縮小到某個組件）
```

### 第三步：止血（15-60 分鐘）

```
決策樹：

如果是最近的部署引起的：
  → DevOps 自動化師：執行回滾
  → 基礎設施運維師：驗證恢復
  → 證據收集者：確認修復

如果是基礎設施問題：
  → 基礎設施運維師：擴容/重啟/故障切換
  → DevOps 自動化師：配合基礎設施變更
  → 驗證恢復

如果是代碼 bug：
  → 相關開發智能體：實現熱修復
  → 證據收集者：驗證修復
  → DevOps 自動化師：部署熱修復
  → 基礎設施運維師：監控恢復情況

如果是外部依賴問題：
  → 基礎設施運維師：啟用降級/緩存
  → 客服響應者：通知用戶
  → 等待外部恢復

全程：
  → 客服響應者：每 15 分鐘更新狀態頁
  → 高管摘要生成器：向利益相關方通報（僅 P0）
```

### 第四步：修復驗證（修復後）

```
證據收集者：
1. 驗證修復解決了問題
2. 截圖證據證明系統正常
3. 確認沒有引入新問題

基礎設施運維師：
1. 驗證所有指標恢復正常
2. 確認沒有級聯故障
3. 修復後監控 30 分鐘

API 測試員（如果是 API 相關的）：
1. 對受影響的端點跑回歸測試
2. 驗證響應時間恢復正常
3. 確認錯誤率回到基線

產出：事故解決確認
```

### 第五步：事後復盤（48 小時內）

```
工作流優化師主持事後復盤：

1. 時間線重建
   - 問題什麼時候引入的？
   - 什麼時候被發現的？
   - 什麼時候解決的？
   - 用戶受影響的總時長

2. 根因分析
   - 什麼壞了？
   - 為什麼壞了？
   - 為什麼沒有更早被發現？
   - 5 個 Why 分析

3. 影響評估
   - 受影響的用戶數
   - 營收影響
   - 聲譽影響
   - 數據影響

4. 預防措施
   - 什麼樣的監控能更早發現？
   - 什麼樣的測試能提前攔住？
   - 流程上需要什麼改變？
   - 基礎設施上需要什麼改變？

5. 行動項
   - [行動] → [負責人] → [截止日期]
   - [行動] → [負責人] → [截止日期]
   - [行動] → [負責人] → [截止日期]

產出：事後復盤報告 → Sprint 排序師把預防任務加到待辦列表
```

## 通知模板

### 狀態頁更新（客服響應者）
```
[時間戳] — [服務名稱] 事故

狀態：[排查中 / 已定位 / 監控中 / 已解決]
影響：[對用戶的影響描述]
當前行動：[我們在做什麼]
下次更新：[預計下次更新時間]
```

### 高管更新（高管摘要生成器 — 僅 P0）
```
事故簡報 — [時間戳]

現狀：[服務] [掛了/降級]，影響 [N 個用戶/百分比流量]
原因：[已知/排查中] — [如果已知的簡要描述]
行動：[正在做什麼] — 預計恢復時間 [時間估計]
影響：[業務影響——營收、用戶、聲譽]
下次更新：[時間戳]
```

## 升級矩陣

| 條件 | 升級給誰 | 行動 |
|------|---------|------|
| P0 超過 30 分鐘未解決 | 工作室製片人 | 增派資源、找供應商升級 |
| P1 超過 2 小時未解決 | 項目牧羊人 | 資源重新分配 |
| 懷疑數據洩露 | 法務合規員 | 評估監管通知義務 |
| 用戶數據受影響 | 法務合規員 + 高管摘要生成器 | GDPR/CCPA 通知 |
| 營收影響 > $X | 財務追蹤員 + 工作室製片人 | 業務影響評估 |
